# 四条标准

按这个顺序回答。前一条已经能定类时，后面的仍然写一句，避免以后重复看同一段代码。

1. 这段代码读写的字段，有没有 spec 变量对应？有，则是 B 类，一定重要。没有，则可能不重要。
2. 它是不是防御性代码（assert 失败分支、NULL 检查、错误返回）？是，则在覆盖率工具标明白名单，之后可以忽略。
3. 它的守卫条件，能不能写成 spec 变量上的谓词？能，则可以交给 TLC 去找路径，但也可能对应一个死代码，永远走不到。
4. 它是不是只在初始化、销毁或配置阶段运行？是，则低优先级，但销毁路径常有资源泄漏类 bug。

## B 类

函数读写的字段已经出现在 `base.tla` 或可执行副本的协议变量里：任期、投票、日志、提交点、快照点、角色、`nextIndex`、`matchIndex`。这类一定重要。

模型里已有动作或同一条守卫：回到采样。30 步里动作名一次都没出现，而消息已经在袋里，优先加长 `DepthBound`，让处理步发生。动作名出现过而函数仍是 0 次，先核对是不是另一条代码路径在做这件事，再加针对该守卫的种子。

模型里没有这些变量：写成场景。说明字段、守卫、以及现有 `Value` 或动作集合为什么产生不了这条路径。

## 防御性分支

assert 失败、空指针、错误码返回、以及「条件下直接 return -1」的拒绝。成功路径已经覆盖时，这些 `#####` 标进白名单。成功路径本身没覆盖时，先按 B 类处理成功路径，不要把整个函数都标成可忽略。

守卫能写成谓词、而 TLC 在放宽界限后仍然找不到状态，在文档里写成可能的死代码，并留下用过的界限。不要凭一次 30 步采样就写成死代码。

## 初始化、销毁、配置

只在创建、设置超时、注册堆函数、或释放对象时运行的函数，标低优先级。驱动若直接写结构体字段、从不调用某个 getter，该 getter 也归这里，并注明协议状态已经由回放比较过的那些变量覆盖。

`free`、`clear`、释放日志和节点的函数低优先级，同时注明：当前 `MCNext` 没有崩溃和恢复，这些路径没有被执行，资源泄漏要等有销毁动作时再看。
