# 失败记录

任何失败立刻追加到 `controlled-execution-runs/<轮次>/failures.tsv`，并通知。列是：

`配置`、`轨迹`、`种子`、`归类`、`退出码`、`logout`、`变量`、`代码值`、`模型值`、`pc`、`记录目录`

归类只写 `adapter`、`bug`、`spec`、`environment`、`crash`。`crash` 在确认之前不改成另外四档。

`base.tla` 常常按源码行号模仿实现，模型值不是协议要求的结果。变量不一致只说明公式和这次执行不同。按下面的顺序归类，不先归 `bug`。

1. **适配层。** 驱动、生成器或序号映射没有把库这次的发送、接收或读回交给比较。证据是库的返回值、发出的字节和控制器交付的内容对不上，或者读到的不是库自己的状态。归 `adapter`。
2. **协议。** 用这个系统应当遵守的规则看库这一步实际发出或收到的内容，以及它写下的状态。规则是该系统的安全性质和消息含义，例如已经提交的内容还在、提交点不超过本机已有日志、已经压缩掉的前缀不再按新下标追加、领导者缺少要发送的条目时发送快照。不在这里点名某一个系统的变量。库违反这些规则，归 `bug`。公式给出的值可能和协议要求不同。README 写协议要求的结果，并写明模型值不是修补目标。
3. **规格。** 库这一步的状态符合协议，差只出在公式多写、少写，或注释引的源码行并没有做公式写的那件事。归 `spec`。不改库去贴公式。发现后按下面的「规格对齐」处理，不把这种差留到交付。

比较通过只说明可见变量相等。两边一起写成偏离协议的值，归 `bug`。

同一条轨迹上，比较失败的那一项可以是 `spec`，另有一条没被这次比较覆盖的路径违反协议。两条分开写。不用「把库改成模型值」去抹平后者。

| 归类 | 接着做什么 |
|---|---|
| `adapter` | 驱动、生成器或序号映射和库的这次调用对不齐。通知并停。修好之后新开一轮次。旧轮次的 gcda 不并入。不查上游 issue。 |
| `bug` | 库这一步违反协议，或两边一起写成偏离协议的值。拷贝文件，查上游，通知后在同一轮次继续。建议修改对准协议要求的结果。 |
| `spec` | 公式和库不一致，库这一步符合协议。通知并停。按「规格对齐」把公式改到与源码一致，再回到 `sandtable-instrumentation` 生成适配层，新开一轮回放。不查上游，不改库。 |
| `environment` | 这一步没有在节点上执行。通知。修好环境后在同一轮次继续。 |
| `crash` | 当前 label 不是受控的崩溃或恢复，而进程非 0、没有 `logout`、容器没有起来、超时，或库 / sanitizer 打出 `Assertion`、`Sanitizer`、`stack smashing`。通知并停。拷贝 `log.host`、`replay.status` 和 sanitizer 输出。受控的崩溃或恢复执行成功时不写这一行。 |

控制器的 `Variable ... compare failed` 是变量不一致，按上面的顺序归类，即使日志里同时有控制器自己的断言。只读后返回错误码、进程仍在的防御性分支不是 `crash`。这条路径把进程打死、且没有变量失败时才先记 `crash`。

`net-len` 警告不是失败，不写入这张表。

## 规格对齐

归类已经是 `spec` 时做这些事。同一条公式差不要把剩余种子跑完。

1. 把对不上的规格从 `<run>/spec/` 拷进当前 `<ce>/spec/`，文件名不变，例如 `base.tla`。`<run>/spec/base.tla` 不改。`<ce>/spec/base.tla` 已经是前一次对齐留下的副本时，在这份上改，不要再用 `<run>/spec/` 覆盖它。和这条公式一起用到的 `MC.tla`、`MC.cfg` 也同样拷进 `<ce>/spec/`。
2. 对齐时只读这份规格和 `<ce>/system/` 里的源码。不读驱动、生成器、`traces.txt` 里的命令，也不按驱动读回的值改公式。失败行只用来指出动作、变量和步号。
3. 公式写成源码这一步实际写下的状态。注释里的行号改成源码里做这件事的行。库违反协议的差留在 `bug`，不在这一步改掉。
4. 每一次修改追加到 `<ce>/spec-repairs.md`。写上配置、轨迹、种子、步号、变量、代码值、模型值、原公式、`<ce>/system/` 里的文件和行号、改后的公式。
5. 回到 `sandtable-instrumentation`。协议公式用 `<ce>/spec/base.tla`，重新生成可执行规格、驱动和生成器。生成适配层时才看驱动。
6. 公式或适配层只要改过，就必须新开一轮次，再在新轮次里采样回放。不能在发现这条错误的轮次里继续回放，也不能把旧 gcda 并进去。旧轮次的 `failures.tsv`、轨迹、`potential-bugs/` 和 `spec-repairs.md` 保留。
7. 新轮次里再出现 `spec` 就从第 1 步做，修好后再次新开一轮。再出现 `adapter` 就按上一表修好，修好后也必须新开一轮。

交出去的那一轮，`failures.tsv` 里没有 `adapter`，也没有 `spec`。`bug` 和 `crash` 可以留下。

## 上游

只查归类已经是 `bug` 的记录。检索该仓库的 issue 和 PR。`potential-bugs/<短名>/README.md` 写 `KNOWN` 或 `NOT_FOUND`，并附链接。

`KNOWN` 保留轨迹和复现命令，不从 `potential-bugs/` 删掉。`NOT_FOUND` 才作为新的潜在 bug 交给 `bug-confirmation`。

`crash` 先保持 `crash`，不查上游。确认时用协议语义，不用模型值当目标。确认是实现违反协议之后，把该行改成 `bug`，README 写明表现是崩溃或 sanitizer，再按上面查上游。确认是公式把一次符合协议的退出写成了别的状态，改成 `spec`，再按「规格对齐」处理。还不能确定时保持 `crash`。

## 潜在 bug 目录

同一类的每一条轨迹都拷进 `<run>/potential-bugs/<短名>/`。`bug`、`spec`，以及确认后改成这两类的 `crash`，都放这里。尚未确认的 `crash` 也先拷进这个目录，归类仍写 `crash`。轮次目录里的 `traces/` 被 gitignore，GitHub 上只保留这里的副本。子目录不要命名为 `traces`。一条轨迹一个子目录，里面放 `MC.out`、`traces.txt`、`log.host`，以及同一次回放的 `replay.status`、`tlc.err`、`tlc.status`。`crash` 再放 sanitizer 输出。

```
potential-bugs/<短名>/
  README.md
  t0158/MC.out
  t0158/traces.txt
  t0158/log.host
  t0158/replay.status
  t0130/MC.out
  ...
```

新开一轮次时不要改已经写好的目录。

`README.md` 写这些事：

1. 配置名、每条轨迹的种子和步号。步号用日志里的 `# [k]`。
2. 不一致的变量、节点、代码值、模型值。两边的值都写上。崩溃没有变量差时，写退出码、信号或 sanitizer 摘要。
3. 库里的位置：`<ce>/system/` 下的文件、函数、行号。
4. 为什么归成这一类。写库这一步实际发出或收到的内容。`bug` 写违反的协议规则，以及协议要求的结果。模型值和协议要求不同时写明，建议修改对准协议要求的结果。`spec` 写哪一条公式和源码对不上，以及库这一步为什么符合协议。
5. 每条轨迹一条复现命令：`run_one_testcase.sh <potential-bugs 里的 MC.out> <节点数>`。写上失败步，以及期望看到的协议结果或崩溃。
6. 归类是 `bug` 时：`KNOWN` 或 `NOT_FOUND`，以及 issue 或 PR 链接。表现是崩溃或 sanitizer 时写明。`spec` 不写这两项。要改的公式写在 `<ce>/spec-repairs.md`，README 指向该文件里的这一次修改。

不改 `<run>/spec/base.tla`。对不上的公式只改 `<ce>/spec/` 里的副本。不改 `<ce>/system/` 或驱动去抹平这条记录。`bug` 交接给 `bug-confirmation` 时带上这个目录。`NOT_FOUND` 才作为新的潜在 bug 交出去。`spec` 按「规格对齐」改完并重新插桩之后，必须新开一轮再回放。发现 `adapter` 或 `spec` 的那一轮不再继续采样。
