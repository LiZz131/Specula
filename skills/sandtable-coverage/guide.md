# 受控执行上的覆盖率

用同一批 `sandtable-replay` 轨迹，记录实现被执行到的行和分支。覆盖率按配置分开累计。换配置时从零开始，同一配置里的下一条 trace 接着累加。

## 输入 / 输出

**输入**：已经能回放的 `MC.out`，带 `--coverage` 的被测库，以及会在进程退出时把计数写盘的驱动。

**输出**：

- 每种配置一条曲线：第 k 条 trace 结束时的行覆盖和分支覆盖
- 曲线封顶的条数、最终百分比、分文件百分比
- 调用次数为 0 的函数，以及 `#####` 的行
- 每条轨迹的实现侧墙钟，与 `sandtable-replay` 用同一次回放

行覆盖取 gcov 的 Lines executed。分支覆盖取 Taken at least once，也就是该分支至少走过一次的比例。Branches executed 是另一列，报告里可以附上，曲线以 Taken at least once 为准。

## 步骤

1. 按 `references/gcov-gotchas.md` 准备库、驱动和退出时的 dump。确认一条短轨迹能写出非空的 gcda，并且库里已知跑过的函数计数大于 0。
2. 每种配置回放前删除该轮的 gcda。回放之间保留 gcda。
3. 每条轨迹结束后，在容器里合并各节点的 gcda，再跑 `gcov -b`。把百分比和墙钟追加到该配置的记录里。
4. 全部轨迹结束后，从最后一份 gcov 列出 `called 0` 的函数。这份清单交给 `sandtable-coverage-gaps`。
5. 切换配置会清掉 gcda。某一配置特有的已覆盖行，要在清掉之前记下来，或在该配置结束时保存一份 gcov 文本。

## 曲线怎么读

第一条轨迹通常就覆盖初始化、选举和普通 AppendEntries。之后缓慢上升，直到某种动作第一次出现，百分比出现一次台阶。快照、加载快照属于这种台阶。

台阶之后长时间水平，表示剩下的代码不在这组 `pc` 能走到的路径上，或者采样太短，消息发出了还没被投递。把「从未执行」和「动作出现过但函数仍是 0 次」分开写进报告。后者优先交给缺口分类。

## 完成标准

每种配置都有完整曲线和最终未覆盖清单。gcda 在进程中途被冻住时，曲线会从第一条就水平，已执行的函数却显示 `called 0`。出现这个形态时先按 `references/gcov-gotchas.md` 修正 dump，再重测覆盖率。轨迹判决本身不用因此重跑，除非回放进程也要换二进制。
