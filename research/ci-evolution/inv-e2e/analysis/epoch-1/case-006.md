## 1. Conclusion

The three arms treat the existing properties in the same direction. All keep `ReadDeliveryJustified`, add next to it a strengthened property that binds the ack to the "request instance", and add a linearizability property. All three also converge on the same definition of a "fresh ack": the ack must be generated after this registration. The arms differ in how complete their evidence and review are:
- **v2 is the most complete.** Every affected property is registered, including those whose helper alone changed (`MessagesWellFormed`, `TypeOK`). It also states that the ack source of `ReadDeliveryJustified` changed (R2), and uses K1 to show that the old property is still true on the defect state, so a new property must be added.
- **v1 is second.** Its `ReadDeliveryJustified` caught an ack source that v1 itself had changed wrongly (the ghost took an intersection), and v1 then fixed it. This is the only helper-drift in this case that actually occurred and was handled correctly. Its weakness is imprecise registration: the new sibling property is recorded as modify, and the ack-source change is written under `ReadyNoInvention`.
- **v0 made one reactive weakening** (`UpdReadAckFreshness`→`UpdReadAckAfterEnqueue`). After re-checking the counterexamples, I think this weakening is correct with respect to the requirement: r1 was too strong, and the counterexample it dropped is not a stale read. So it did not hide the defect. But its rationale mixes in implementation-as-requirement wording ("the implementation correlates only by ctx"), and it has no separating-state evidence. For the existing properties v0 wrote only one sentence, "V0 properties retained", with no per-property review. It also made one unrecorded slight weakening in the message part of `TypeOK`.

The earlier per-case notes (not in this repository) said that v0's dropped counterexample "is exactly the defect mechanism". That statement needs correction; see section 6.

## 2. Update summary

- The source changed in one line: in `advance` at `read_only.go:103`, the key used to delete the pending entry changed from `rs.req.Context` to `rs.req.Entries[0].Data` (`diff old-tree buggy-tree`). A new test `TestRaftFreesReadOnlyMem` was also added (`raft_test.go:1249-1296`).
- In the old code the request carried no Context, so after release the entry stayed in `pendingReadIndex`, and a repeated ctx was ignored by the dedup guard. After the update the entry is really deleted, so the same ctx can be registered again within the same term.
- `recvAck` matches only by ctx, so a delayed heartbeat response from the previous registration can count toward the new registration. If a new leader has committed in the meantime, the old leader returns a stale read index (MC-1).
- Affected model elements: the pending release in `HandleHeartbeatResponse`; the dedup semantics of `ProcessReadIndex`; the ghost proof source in `HandleReadIndexResponse` (the old model read the leader's current pending; after the update the entry is gone, so all three arms changed it to read the release history); the meaning of `pendingReads.acks` (from "the acks of the single registration" to "the acks received since the latest registration of this ctx, which may include acks of an older registration").
- All three arms also fixed the V0 problem that `raft.reset` did not clear the read state. v1 and v2 also fixed the term/role rule of `HandleReadIndexResponse` (R3). v0 additionally fixed the progress reset in `BecomeLeader` and `Crash` dropping unpersisted messages (reactive).

## 4. Per-arm summary

**v0**
- Good: in the generation stage it designed S6b (a delayed ack across a reuse, with a new leader committing after a partition) as a scenario (`analysis-report.md:233-243`). All 7 update canaries were witnessed. While looking for a linearizability counterexample, it found that the VIEW dropped the counter, which made BFS miss paths. It verified this with `diag/PathCheck.tla` and removed the VIEW. The Crash fix has a code basis and the regression was rerun.
- Problems: the r1→r2 change is a reactive weakening. The conclusion is right, but the evidence is reasoning plus implementation behavior. Unlike v1/v2, it did not construct a separating state and compare against the requirement. The conclusion was right this time. In another case the same process could drop a real defect. It did not review the existing properties one by one. There is one unrecorded slight weakening in the message part of `TypeOK`. The requirement citations of the new properties mostly stop at implementation lines.
- Under-reaction: the ack source of `ReadDeliveryJustified` changed, but v0 treated it only as a model-fix record and did not go back to the meaning of the property (helper-drift not reviewed, though the result is harmless).

**v1**
- Good: every new property has a separating state plus a control, and most come from real traces. `ReadDeliveryJustifiedFresh` and `ReadIndexFreshness` were violated on real implementation states already in the trace validation stage (timeline [124]-[126]), but v1 recorded them as bug candidates and did not change the properties (`changelog.md:82-85`). When its own ghost production logic was wrong and the old property caught it, v1 first decided "wrong fix or real bug" before acting, and did not weaken the property.
- Problems: the ledger records "keep the old property and add a strengthened one" as modify. The ack-source change is registered under `ReadyNoInvention`. The trace adapter still compares only counts.

**v2**
- Good: every existing property has a REQ-EVIDENCE block and `watch_touched`, including those with only a helper change. The effect of R2 on `ReadDeliveryJustified` is written next to the property. K1 explicitly argues "keep and add" rather than "modify". The trace adapter compares exactly and is tested with mutants. Every new property cites a contract or document.
- Problems: no obvious problem. `UpdReadIndexLinearizable` takes the lower bound at registration time, not at the time the caller issued the request. The comment already states that this is stronger than the contract (the note of this property in `Update.tla`). This is the standard ReadIndex guarantee, so it is not judged too-strong.

## 5. Missed-report attribution

**No missed reports.** All three arms report the same defect, MC-1, and all give evidence that it reproduces on the update and not on the baseline. The paths to it differ:
- **v0 found it through MC first.** It first ran a hunt with the r1 property and hit a too-strong counterexample ([170]). After relaxing to r2, the property was violated again at 21-22 states ([192]). The stale-read consequence was found by a guided hunt with the VIEW removed ([279]-[285], 37 states). Traces `delayed_ack` and `stale_read_reuse` give implementation-side witnesses. v0 did not run bug-confirmation.
- **v1 found it through traces first.** When the generation-stage traces `read_reuse` and `stale_read` were replayed, the two new properties were violated ([124]-[126]). MC focused detected it at 22 states ([172]), the guided hunt at 37 states, and the unguided simulation independently at 44 states. v1 ran bug-confirmation and reproduced it 3/3 vs 0/3 ([237]).
- **v2 also found it through traces first, and earliest.** On the first run of validate.sh, `TrFinalReadAckFresh` was violated on trace `stale_ack_reuse` ([120]). It then fixed the separating state with an evidence cfg. MC detected `UpdReadAckFresh` several times after [143], and the directed hunt detected a linearizability violation at [248]. v2 also ran bug-confirmation.

The difference comes mainly from the exploration path and the order of the process (v1/v2 evaluated the new properties on real traces first). It is not that the overlay decides whether detection is possible. The overlay's effect shows in this: v1/v2 defined the correct "fresh" semantics from the start, with no too-strong intermediate version like r1 that had to be relaxed afterwards.

## 6. Corrections to the mechanical table (`analysis/out/prop_events-case-006.md`)

1. **Missed helper-drift.** `ReadDeliveryJustified` and `MCReadDeliveryJustified` are marked "same", with no helper change, in all three arms. In fact, `HandleReadIndexResponse`, the producer of the `publishedReads[k].acks` they read, was changed in all three arms. The closure analysis tracks only operators, not the actions that produce a variable, so it missed this. In v1 this even triggered a violation.
2. **Characterization of helper-only rows.** `MessagesWellFormed` and `MCMessagesWellFormed` (v0, v2; the helper is `MsgWellFormed`) only gained the value domain of a ghost field. This is a benign change. `TypeOK`, `MCTypeOK`, `TraceTypeOK` are representation changes, but v0's `TypeOK` also has a slight weakening of the message record shape that the table does not show. The helper list of `TraceCanProgress` is "all actions" and its meaning did not change. What changed is the strength of the replay check: stronger in v0 and v2, essentially unchanged in v1.
3. **v0's within-run weakening is invisible.** `UpdReadAckFreshness` (r1) was replaced by `UpdReadAckAfterEnqueue` during the run. The table has only the final state, so this weaken of v0 is entirely invisible.
4. **Where v1 registered.** The `ReadDeliveryJustified` row of v1 has no ev. The registration is in fact in the `replaces` field of `ReadDeliveryJustifiedFresh` (modify). The `affected_because` for the ev keep of the `ReadyNoInvention` row actually describes the ack-source change of `ReadDeliveryJustified`.
5. **New-property counts mix in canaries and aliases.** Substantive new properties: v0 has 5 (7 of its 12 are canaries), v1 has 4 (4 of its 8 are canaries), v2 has 4 (of its 18, 6 are canaries, 7 are `Tr*` aliases or trace oracles, and 1 is the `UpdControlElectionSafety` alias).
6. **cfg counts do not mean coverage.** The "cfg 3→3" of v2's existing properties and the "3→11" of v0 cannot be compared directly. v2 uses one `Trace.cfg` template and swaps the trace file through `IOEnv.JSON` (`JsonFile` in `Trace.tla`); v0 has one cfg per trace. The MC aliases are checked in all `Update_*.cfg` files in all three arms (I verified `Update_full.cfg` and `Update_focused.cfg`).

**Correction to the earlier notes.** Section 3 of the earlier per-case notes (not in this repository) says that the r1 counterexample is "exactly the mechanism of the defect itself", and that v0 "weakened, without evidence, exactly the property that reports the bug". After checking the two counterexample summaries: in the r1 counterexample, the response of s3 is generated after the re-enqueue (step 20 > step 18), so it is not a stale read. It shares the code path "match only by ctx" with the defect, but it is not an instance of the defect. The real defect instance is a response generated before the re-enqueue, and r2 still catches it. So this weakening is correct with respect to the requirement. The problem is only the form of the evidence. The same note also says that r2 "is violated at step 22". The changelog says 22 states and the counterexample summary file says 21 states. The two disagree. The raw TLC log should decide; not verified.

## 7. Uncertain and unverified points

- Whether the r1 weakening is correct rests on the standard Raft ReadIndex argument: if the follower is still in the leader's term when it generates the response, a higher-term leader cannot have completed a commit before that. I did not verify on TLC that no stale read appears when the r1 counterexample is extended.
- v0's Crash fix does not appear in v1/v2. I did not verify whether the v1/v2 models still carry this V0 defect without triggering it. This needs a check of whether the MC.cfg of v1/v2 gives a crash budget, and of the check results of `MCLeaderCompleteness`.
- v1's trace compares only pendingCount/readCount, so the read index values that E2/E3 rely on are computed by the model and are not compared with the implementation record by record. v1's reproduction test gives index 1 < committed 3 on the implementation side, which partly makes up for this.
- `UpdQueueNoDuplicates` and `ReadQueueDistinct` are judged untested because the dedup guard makes them true by construction. I did not check one by one whether a model path exists that bypasses the guard.
