Rubric: [rubric](rubric.md) (epoch-1). ## 1. Conclusions

None of the three arms changed the formula text of the 11 existing properties. Only TypeOK gained type constraints for the new variables (v0, v1). All three arms reported the same update-introduced defect, MC-1: after calling transfer_leader on a learner, the learner starts an election and panics in `Candidate::grant_by` while handling its own vote. The differences are in the reaction to "changed preconditions and reachability".

- **v0 reacted most fully.** Its reconnaissance phase already listed three new kinds of reachable `elect()` initiators: non-voters, removed nodes, and the current leader. v0 wrote "a learner does not elect itself" as the action property `ElectOnlyByVoter`, which is equally valid for removed nodes. It also added `LeaderVoteNotSuperseded`, which replaces the premise of `LeaderVoteCommitted` from `role="Leader"` with `leader[n]`. This closes a blind spot of the original property, and it reports MC-2: transferring to the current leader triggers a debug assertion (already present in the old code; the update adds a new path that triggers it).
- **v1 is in the middle.** Its action property `ElectionInitiatorIsVoter` also covers removed nodes, and v1 separately reports "when the target is a removed node, the cluster is disturbed". Its keep evidence is the most solid, based on real traces. But it did not examine the path where the current leader transfers to itself: `TransferTargets={2,3}` in the main cfg excludes the initial leader.
- **v2 under-reacted in two places.** First, the new `ElectionByVoterOnly` says in its intent "neither learners nor removed nodes start an election", but its formula is `candidate[n] ⇒ …`. v2's own `Elect` sets `candidate` of a non-member node to FALSE, so this property cannot see removed nodes; the representation is not faithful. In addition, all cfgs have `MembershipLimit≤1`, so removed nodes are not reachable at all. Second, leader self-transfer was recorded only as CR-2 in code review and not written as a property. On the good side: using the storage contract in a comment, v2 fixed a durable-commit counterexample that already exists in the old code as a model defect (v1 marked the same mechanism only NEEDS MORE INFO); its keep evidence also states most explicitly that "the canary and the check config use the same set of constants".

All three arms made several **model-level narrowings** that shrink the checked scope of existing properties, but each gave a code or contract source. The mechanical table looks only at formula text and records all of them as `same`. The mechanical table also has a parsing defect: in a cfg, a `PROPERTIES` section written after `INVARIANTS` is dropped entirely, so 3 new properties of v0 and 3 of v1 are undercounted (see section 6).

## 2. Update summary

- A new handler branch for `RaftMsg::TransferLeader{from,to}` (`WORK/subjects/case-004/buggy-tree/openraft/src/core/raft_core.rs:1190-1202`): if `vote == from`, it runs `vote.disable_lease()`; if in addition `self.id == to`, it calls `engine.elect()` directly. **It lacks** the `is_voter` guard that both tick and `ExternalCommand::Elect` have (`raft_core.rs:1206-1214`, `1454-1457`).
- A new public API `Raft::transfer_leader(from,to,flushed_log)` (`raft/mod.rs:635-703`): the target node sends the message after its log is flushed (or after a timeout); the documentation requires calling it with the same arguments on every node.
- `Leased` gained `lease_enabled` (`utime.rs`): `disable_lease` turns the lease off, `touch` does not turn it back on, `update` does.
- New test `t14_transfer_leader.rs`: after a transfer to a voter it becomes leader; a transfer initiated with an old vote has no effect.
- Affected model elements: the enabling condition of the election action (a new caller without a voter guard), the post-state of `Elect` for non-member nodes, vote-response handling (`grant_by` panics for non-quorum members), and the lease (the old model abstracts the lease as "a vote can always be granted"). Changes to metrics and Display have no effect on the model.
- The old model merges the voter guard and `Engine::elect` in one `StartElection` (`IsVoter(n,n)` in `StartElection` in `OLD/base.tla`), and the MC has `ElectionLimit=1`, `MembershipLimit=1`. So the states "multiple elections", "leader elects again" and "node removed" were already unreachable in the old model.

## 4. Per-arm summary

**v0 (166 minutes, $22.58)**
- Good: the reconnaissance phase listed all three new `elect()` initiator kinds at once (`analysis-report.md:33-36`). It used an action property to express "a learner does not elect itself", which has the widest scope. It found the premise blind spot of the old property `LeaderVoteCommitted` and closed it with `LeaderVoteNotSuperseded`, thereby detecting MC-2. Fixing R8 was reactive, but before fixing it v0 read the code (the FIFO notification channel in `raft_core.rs`) and re-derived the counterexample; it did not simply explain the violation of `ElectedLeaderWasVoter` away.
- Problems: the two lease properties only check the model's own bookkeeping and do not help find defects. `LeaderCompleteness` compares only two leaders in office at the same time, which is weak, and has no reachability evidence. `TransferSafety` is a dead definition in no cfg. When `LeaderVoteNotSuperseded` was added, the remaining campaigns were already running, and none of them checked it (`changelog.md:122-123`).
- Under-reaction: basically none. The removed-node path is covered by `ElectOnlyByVoter` and `CanaryAbsentElect`, but v0 did not report its consequence (disturbing the cluster) separately.

**v1 (145 minutes, $26.50)**
- Good: the combination of an action property and a state property, with an honest note that the state property covers only present members. Every added property has a constructed divergence state, a control group and a real trace. Keep also has real-trace evidence (E3-keep), and the new traces were replayed against the V0 suite as repair evidence (`repair_evidence` R-V0-replay). "Own vote first" was built into the model proactively in the generation phase. The removed-node variant was reported separately. When DurableStateBounded was violated by a counterexample unrelated to the update, v1 kept the property, removed it only locally from two hunt/canary cfgs, and reported the counterexample as MC-2.
- Problems: the main cfg excludes the initial leader with `TransferTargets={2,3}` and no reason is given. Its MC-2 (persisted committed is ahead of the leader's durable log) does not cite the IO serialization rule in the storage contract and may be a false positive; v2 has a contract source on the same point. The mechanical table cannot see v1's keep evidence, because v1 writes several properties in one entry.
- Under-reaction: the premise of `LeaderVoteCommitted` has a blind spot in the newly reachable state "leader elects again"; v1 did not examine it and did not find the assertion of MC-2.

**v2 (103 minutes, $22.05, the fastest of the three arms)**
- Good: the REQ-EVIDENCE annotation was really used. New properties have complete requirement sources; the `SaveCommit` narrowing cites the storage contract and its judgement is more accurate than v1's. The keep evidence says explicitly that the canary and the controls use the same constants, so one can confirm that the "commit after transfer" state was indeed checked by the existing properties. `CanaryLearnerLeader` was used as a reverse check; after a witness appeared in round 1, v2 reviewed the code before fixing the model.
- Problems: the intent and the formula of `ElectionByVoterOnly` do not match (removed nodes); `MembershipLimit≤1` in the cfgs makes removed nodes unreachable, and these two gaps stack. `TypeOK` has no type for `panicked` (minor).
- Under-reaction: (1) reconnaissance described the removed-node path, but it was later written into no property, cfg or canary, and v2 did not report the variant that v1 reported; (2) leader self-transfer was recorded only as code review, the model keeps the `LeaderAppend` guard that makes it invisible, and the original property `LeaderVoteCommitted` was not strengthened.

## 5. Missed-bug attribution

No missed bug. All three arms reported MC-1, by different routes:

- **v0 was model-driven.** Before writing the model, v0 read `Candidate::grant_by` at [77], so the generation phase already added the panic branch (fix R3) and `NoCorePanic`. In MC, Update_full first violated `ElectOnlyByVoter` ([192]), then `NoCorePanic` ([195]), and only afterwards was it confirmed with a real trace and a 5/5 uninstrumented reproduction. The harness also independently observed this panic at [155].
- **v1 was code-reading-driven.** Reconnaissance already proposed `ElectionInitiatorIsVoter` ([78], [97]). In the middle of generation it read `error.rs` and `candidate.rs` ([170]-[173]) and added the panic modeling; the live cluster then reproduced it at [197], and MC gave the counterexample at [321].
- **v2 was run-driven.** The generation phase had only `ElectionByVoterOnly`. The panic was observed while running the learner-transfer scenario ([157]-[161]); only then were `CandidateGrantPanic` and `NoRaftCorePanic` added, and MC confirmed it afterwards.

In all three routes the defect mechanism was determined at the code level before the first TLC campaign, so this case cannot tell what the overlay rules contributed to detection. The difference shows only in side findings: v0's MC-2, v1's removed-node variant, and v2's CR-2.

## 6. Errata for the mechanical table (`E/analysis/out/prop_events-case-004.md`)

1. **`PROPERTIES` is dropped (parsing defect).** The regex `(INVARIANTS?|PROPERT…)((?:\s+ident)+)` in `check_annotation.properties()` swallows the following `PROPERTIES` keyword as an identifier inside the `INVARIANTS` section, and on meeting the keyword it does `break`, so the whole set of action properties is lost. I confirmed this by recomputing with `python3 -I` on `v0/…/Update_full.cfg`, `v1/…/Update_full.cfg` and `v1/…/Update_discharge.cfg`. The undercounted ones are: for v0 `ElectOnlyByVoter`, `LeaseReenabledOnVoteChange`, `DisabledLeaseOnlyByTransfer`; for v1 `ElectionInitiatorIsVoter`, `DischargeContext`, `PartitionComplete`. `DischargeContext` of v0 and v2 is counted only because their discharge cfgs contain only a `PROPERTIES` section. This defect likely affects other cases too.
2. **The counts of additions mix canaries and aliases.** v0's 15 = 9 canaries + `MCLeaderCompleteness` (alias) + 5 substantive properties; adding the 3 undercounted ones, the substantive additions total 8 (aliases not counted). v1's 8 = 6 canaries + 2, so 3 substantive additions, plus 2 methodological properties (DischargeContext, PartitionComplete). v2's 11 = 8 canaries (of which `CanaryLearnerLeader` is a reverse check) + 2 substantive properties + `DischargeContext`.
3. **The empty evidence column for v1 is an artifact.** v1's keep entry writes several properties together as `"CandidateGrantSound / LeaderVoteCommitted / …"`, and the script matches by single property name, so nothing matches. v1 in fact registered keep evidence (E3-keep and MC logs) for all existing properties.
4. **`TypeOK changed` (v0, v1) is only a representation change**: type constraints for new variables, not a semantic change.
5. **"All same" hides model-level narrowings.** For example: the MaxIndex election bound in all three arms; "own vote first" in all three arms; v2's `SaveCommit` flush guard; v1 removing DurableStateBounded from two cfgs; v1 excluding leader self-transfer in the main cfg; v2's MembershipLimit making removed nodes unreachable. None of these is in a formula, so the mechanical table cannot see them.
6. **`cfg 1→N` does not mean strengthening.** Most of the increase is new Update_* cfgs. v2's `MCLearnersExcluded` and `MCMembershipWellFormed` are `1→1`, but this does not mean "not checked on states with a transfer": v2's `MC.cfg` itself has `TransferLimit=1`.
7. There are no "deleted" false positives caused by renaming or module changes.

## 7. Uncertain and not verified

- Whether v0's Update_full actually met the "leader commits after transfer" state in its BFS: I inferred this from the BFS depth 27 being greater than the witness depth 22 and the witness cfg's actions being a subset of the wide config; there is no direct evidence.
- `LeaderVoteNotSuperseded` and MC-2 rest on a `debug_assert`, which fires only in debug builds. Whether treating it as a "requirement" is valid depends on whether internal assertions count as a contract. I judged it correct, but with moderate confidence. v2 states the trigger as "a client write follows", which is not fully consistent with the fact that `raft_core.rs:967` calls `leader_handler()` on every loop iteration, though both reproduced it on the real code.
- v2's `SaveCommit` guard assumes `save_committed` is also a write IO that must be "serialized". The contract text names only vote and log IO. So whether v1's MC-2 is a false positive I can only say I lean toward yes.
- For v0's fixes R1, R4, R5, R6, R7 and v1's R1-R4, I only checked the source notes in the changelog and a few source lines; I did not verify them line by line.
- I did not run TLC myself. The state counts and violation status of each campaign follow the run logs and summaries.
- Whether "LeaderCompleteness or an election safety property should be added": the old property set did not have one, and the update adds a new path to a new term, so adding one is a reasonable strengthening. But its requirement source is only common Raft knowledge, so I do not judge v1 and v2 as missed for not adding it.
