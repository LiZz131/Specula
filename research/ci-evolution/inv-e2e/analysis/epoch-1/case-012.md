## 1. Conclusion

**Evolution quality.** None of the three arms changed a property's text in order to remove a "bug-reporting" counterexample. The real difference is in the oracle design of `CommitWitnessSound` (CWS):
- **v0, v1** changed the witness so that it is computed independently from `matchedIndex` (the real acks of ReplicationState), decoupled from VecProgress (v0 `base.tla:293-296`, v1 `base.tla:272-277`). CWS thus became an independent oracle that checks the VecProgress result; MC-1 was detected by it and by the newly added `ProgressSortedAboveCommitted`. The cost: both groups clear the witness at `StartElection`, a small model-narrowing, and no reason is registered for it.
- **v2** replaced the V0 CWS with `CommitWitnessSound_new`. The replacement itself has separating-state evidence evaluated by TLC, and it keeps the witness across terms, which is stronger in checking strength than what v0 and v1 do. But v2 makes `matchedIndex` equal to the VecProgress value (`changelog.md:29`), and commit and witness are computed from the same rows with the same set function, so the quorum clause in `_new` holds **by construction** in v2's own model and has no power to detect a commit-quorum error. This point is visible neither in the mechanical table nor in the earlier analysis.
- The three groups treat the `OneOutstandingMembership` (OOM) restart problem differently. v0 rewrites it as `…Durable`, which weakens the formula, but it covers the cfgs with crash, and the evidence is only the implementation code. v1 and v2 keep the original text and check it only in cfgs without crash. v1 uses "the V0 model is violated as well" as a control; v2 registers it honestly as unresolved.

**Root cause of the miss (one sentence).** v2 carried over the old model's decision that "the internal order of VecProgress is an optimization detail that can be abstracted away". The premise of that decision is "the production commit path uses `greatest_majority_value`". The update deleted that function, so the premise no longer holds, but v2 did not recheck it. It also wrote the documented contract of VecProgress ("take the greatest quorum value") directly as the commit semantics, and closed with a "new and old commit values are equivalent" argument. It says this argument is "later checked by trace validation", but the trace design makes that check unable to fail. v2 did read the key code, and even modified it, so this is not unread-code.

## 2. Update summary

- The leader's commit computation moves from `LeaderState::calc_commit_log_id` (which recomputes with `greatest_majority_value` over all matched values on every ack) to `Engine::update_progress` (`S/buggy-tree/openraft/src/engine/engine_impl.rs:618-648`), owned by the leader's `VecProgress`. `greatest_majority_value` is deleted.
- The code of `VecProgress::update` is almost unchanged (the diff has only the unknown-id return, the `quorum_set()` accessor, and `upgrade_quorum_set` dropping the `safe_index` filter). But in the old tree it had **no production caller** (`grep VecProgress S/old-tree/openraft/src` has no hit outside `progress/`); this update wires it into the commit path.
- Latent defect: when `prev > committed`, the value is raised in place without `move_up` (`progress/mod.rs:180-185`), while the prefix scan assumes the values above committed are in descending order (doc `:58-59`, scan `:187-201`). `upgrade_quorum_set` replays in ascending id order (`:222-232`); on ties a follower with a lower id is placed before the leader, and a later in-place raise then breaks the order.
- Affected model elements: `HandleUpdateMatched`, `LeaderAppendEntries` (update_progress once before and once after the membership entry, with an upgrade in between), `StartElection`/`GrantVote` (progress is rebuilt per term, vote quorum now reads the progress quorum set), the follower's committed-membership promotion (only when commit advances), CWS which reads the matched rows, and `MembershipOrder`/OOM which read membership.

## 5. Miss attribution (v2 misses MC-1)

### 5.1 Where the wrong abstraction comes from: inherited from the old model and widened to the commit path

- Wording of the old model: `O/spec/base.tla:402-405` "Direct form used to validate VecProgress's externally visible update relation; its sorted-vector layout is deliberately abstracted away"; `O/modeling-brief.md:97` "`VecProgress` internal vector ordering | … model externally meaningful per-node values rather than the optimization layout"; `O/analysis-report.md:55` gives the premise "because the scoped leader commit path uses externally meaningful `BTreeMap<NodeId,LogId>` plus `greatest_majority_value`". The old `Trace.tla:126-129` `ProgressMatches` compares only id→value and committed, not the order.
- In the old model this abstraction was used only for the trace-only `ProgressUpdateValue`, and commit went through `GreatestCandidateOrOld`, which corresponds to `greatest_majority_value`. So the old abstraction was safe at the time.
- The final v2 model (`E/v2/output/spec/base.tla:163-180`) writes the same set function as the **production commit semantics**: `GreatestQuorumValue`, with the comment "VecProgress keeps `committed` equal to the greatest stored value v such that the ids whose value is >= v form a quorum". That is, the old `greatest_majority_value` semantics is attached to VecProgress unchanged. `UpgradeRow` (`:184-189`) only copies values and does not express the replay order. The line `modeling-brief.md:97` is kept unchanged (all three groups kept it, so this line is not itself the difference).
- Conclusion: **inherited**, and widened. The old abstraction applied to "a trace-only helper function"; v2 applies it to "the production commit path", where the premise no longer holds.

2. **Model checking.** There is no order in the model, so the defective state is unreachable. Keeping SYMMETRY has the same source. The U-S1 canary reaches a neighboring scenario, "the leader appends and commits index 1 using n3's earlier ack"; at [309] v2 judged "safe because every config pair in the 3-node universe intersects", which is correct in the idealized model.
3. **Properties.** The quorum clause of `CommitWitnessSound_new` holds by construction in the v2 model (section 3). Even if another path made commit wrong, it would not catch it; and the model has no VecProgress representation invariant.
4. **Completeness review.** It checked only the branches in the diff (section 5.2). ### 5.7 Minimal interception point

**Step: the decision gate of 01 reconnaissance. Object: every row of the abstraction/exclusion table of the old brief, and every "deliberately abstracted" comment in the old spec. Artifact: an "inherited abstraction premise review table".** Each row states: which symbols or call paths the premise of the abstraction cites; whether the diff deletes or reroutes those symbols, or adds a production caller to the abstracted function; if so, a **differential execution** (real function against the model operator, exhaustive on small inputs) is attached, and only then is it decided whether to keep or refine.

- This can be triggered mechanically: the premise at old `analysis-report.md:55` names `greatest_majority_value`, and v2 itself recorded it as "deleted" in U9 (`:90`). A string comparison is enough to flag this row.
- Differential execution is cheap: I ported `VecProgress::update`/`move_up`/`upgrade_quorum_set` to Python line by line and enumerated update sequences of up to 4 steps on the joint quorum set `[{1,2,3},{1,2}]`, and found a divergence from `GreatestQuorumValue`: the sequence `(1,1),(3,1),(3,2),(2,2)` gives committed=2 in the implementation, whereas the ideal value is 1. In Rust this is a unit test of about 20 lines; v1 wrote a similar old-control at [224].
- A second-level interception point (trace step): if the equivalence argument says "tested by trace validation", it must write down the branch and state condition it depends on (here: "an in-place raise with `prev > committed`, with a lower-id node tied and placed before the leader"), prove that at least one trace satisfies this condition, and forbid preprocessing from deleting the events that carry the condition.
