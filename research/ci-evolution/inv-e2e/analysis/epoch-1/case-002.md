## 1. Conclusions

The three arms treat the existing properties differently mainly because they represent the "in-memory data tree" differently. v1 redefined `applied` as the in-memory data tree. As a result, it changed 4 existing properties on its first model write ([95]): 3 weakened, 1 strengthened. The evidence was added afterwards, in [237]-[302], and is mostly acceptable. But the "requirement source" cited for PipelinePrefix is in fact the old model's own fail-stop assumption. v2 added a ghost variable `memHist` to represent the data tree and kept `applied` with its original meaning. So no existing property was weakened in MC, and only SyncCompletionJustified was strengthened. The only "revision" v2 made targeted its own new SyncedLogMatchesLeader, and it was a weakening, not a strengthening as the earlier analysis says. v0 changed the semantics of Crash, which triggered Case A. It then weakened PipelinePrefix twice without evidence (once proactively, once reactively). In addition, v0 and v2 both replaced OneActiveLeaderPerEpoch in Trace.cfg with a weaker trace-only version, and neither registered it. v2's evidence file even says "keep (unaffected)".

Root cause of the missed bug: **v1 did not simply fail to model "COMMIT received during sync".** Its final model has `ReceiveSyncCommit`, and the precondition state of the NPE is reachable (after NEWLEADER, `syncBuf` (that is, packetsNotCommitted) is empty, a COMMIT arrives, and the action can fire). I found this state with TLC at depth 38 in 27 seconds (see §5.4). The problem is that v1 wrote the action according to what the COMMIT branch "should do" (`packetsCommitted.add`). It missed the unconditional, null-unchecked `packetsNotCommitted.peekFirst().hdr` that runs before the branch. It also has no state or property that represents the exception, and its trace probe sits after the dereference. Classification: contract-substitution plus property-gap. It is not scope-exclusion and not budget.

## 5. Missed-bug attribution (v1 did not report "NPE when COMMIT interleaves with NEWLEADER")

### 5.1 Where the wrong abstraction came from

- The old model had no place for this interleaving: sync is the atomic `CompleteSync` (`OLD/base.tla:206-230`), there is no packetsNotCommitted, and sync only happens with a leader in the sync phase (`OLD/base.tla:175`, `:192`). The old model's COMMIT action also wrote "the next proposal must match" as an enabling condition (`OLD/base.tla:407-412`: `proposed[m.to][Len(committed[m.to]) + 1] = EntryFor(m.id, m.epoch)`). That is, the old model's style already treated a check in the implementation as a condition for whether the action can happen.
- v1 **newly introduced** this action, and did not inherit the old model's scope limit: `Forwarding` also counts learners in the sync phase (base.tla:175-179), `LeaderHist` carries `Outstanding(l)` when RUNNING (base.tla:131-134), and `Commit` sends COMMIT to learners that are syncing (base.tla:874-890). Its `ReceiveSyncCommit` (base.tla:558-587) only does `syncCommits' = Append(@, e)` in the writeToTxnLog branch and never looks at whether `syncBuf` is empty. In the SNAP/TRUNC branch it writes `syncBuf /= <<>> ∧ Head(syncBuf) = e` as a guard. Both forms abstract away the implementation's null-unchecked `peekFirst().hdr`; the latter follows the old model's style of "writing the check as a guard".
- Conclusion: the wrong abstraction was newly written by v1, with anchoring on the old model's guard style.

### 5.2 At which step it was fixed

- It was fixed in the reference-model phase (02), on the first write of `base.tla` ([95]). The body of `ReceiveSyncCommit` matches the final version (the text written at [95] already contains `ELSE /\ syncCommits' = …`) and was never changed afterwards.
- The reconnaissance phase (01) already contains the blind spot. analysis-report.md:30-35 says "records received after NEWLEADER are still logged and all `packetsCommitted` are committed afterwards (L:777-785, unchanged)", which concerns where the **records** end up. The before/after table (analysis-report.md:41-49) has 5 rows, none about the COMMIT branch.
- The four interactions of the update-analysis phase (03) (analysis-report.md:115-133) are all of the types "records and persistence, ACK and activation, INITIAL shutdown". Update.tla:21-25 annotates another piece of code that is "unchanged but newly reachable" (`canShutdown`), but gives no such analysis for the COMMIT branch. `MCReceiveSyncCommit` is listed in `InteractionActions` (Update.tla:65), but the action itself is written with "optimistic" semantics.
- The agent's own words never discuss null handling in the COMMIT branch (`peekFirst|NPE|NullPointer` appears 0 times in v1's own text in the whole log).

### 5.3 Information gap: what was read and what was not

- Read: [17] `grep -n "syncWithLeader" -A 260 quorum/Learner.java`, which covers lines 643-669 where the COMMIT branch is. [93] collected line-number anchors for the COMMIT and other branches. At [130], when changing the instrumentation, the whole COMMIT branch was read and written as the replacement anchor (`instrumentation/artifact.diff:147-167`).
- So this is not unread-code: the code was read, but it was read for "what this branch should do".

### 5.4 Why the mechanisms that should have caught it did not

- **The interleaving is in fact reachable in the model.** I copied v1's final `base.tla` and `MC.tla` unchanged into the scratchpad and added a single canary, without modifying any run output:

  ```tla
  NPEWindowNotReached ==
      ~\E m \in messages :
          /\ m.kind = "commit"
          /\ syncJustified[m.to] /\ nlAckSent[m.to]
          /\ syncBuf[m.to] = <<>>
          /\ ENABLED ReceiveSyncCommit(m)
  ```

  Configuration: `Server={s1,s2,s3}`, `Txn={t1}`, `MaxEpoch=1`, no fault injection, `MaxDepth=60`, symmetry on. TLC BFS ran for 27 seconds and the canary was violated at **depth 38**. The path: s2 first completes one round of sync, then does BeginElection and follows s1 again; after s1 activates, `Propose(t1)`; s2 executes `SyncDiff` (puts t1 into syncBuf as Outstanding), `PersistCurrentEpoch`, `ClearSyncMode`, `StartupWithoutServing`, `LogSyncProposal` (syncBuf is cleared), `SendNewLeaderAck`; then `Commit(s1,t1)`. At this point `ReceiveSyncCommit` can fire, but the model just appends t1 to `syncCommits` and reports no error. The probe files were in the scratchpad (a temporary directory that may be cleaned; the full text of the canary is given above and the files are not kept). This shows that the claim "v1 did not model COMMIT received during sync" is wrong: the interleaving is in the model, but the model treats it as a normal case.
- **Trace coverage**: validation-summary.md:63 states that `ReceiveSyncCommit` is covered only by follower-snap (an inherited fixture). The order in that trace is `NewLeaderAckSent(11) → SyncProposalReceived(12) → SyncCommitReceived(13, "buffered")`, that is, a new PROPOSAL arrives **first** after NEWLEADER. This is the safe order. None of the traces has the order "PROPOSAL before NEWLEADER, COMMIT only after NEWLEADER" (I counted 6 traces).
- **Properties**: v1 has no state or property that represents an exception or a sync abort. Even if the action were written faithfully, TLC would not report an error as long as the model has no flag like `syncError`.
- **Completeness review**: brief-coverage.md:43-46 lists only Q5, Q6, plus CR-A (liveness) and CR-B (shutdown order). There is no COMMIT-related canary and no explained-away counterexample.
- **Time budget**: the abstraction was fixed at [95], before the evidence work started. Of 593 turns, 35 of 270 tool calls were evidence-related, the first at [237]. There is no evidence that evidence work crowded this analysis out. Much of v1's later time went to reproducing LeaderCompleteness, FocusInit and several campaigns, but that is a separate issue.

### 5.6 Classification

- **contract-substitution (primary cause)**: the action was written by what the branch "should do", and the probe was tagged by outcome, missing the unconditional dereference before the branch.
- **property-gap**: there is no exception or abort state and no property like `NoSyncException`, so even a reachable interleaving reports nothing.
- **anchoring (secondary)**: it follows the old model's style of "writing implementation checks as guards" (`OLD/base.tla:407-412` versus v1 base.tla:570).
- **Not**: scope-exclusion (v1 lifted the late-join limit and the interleaving is reachable), interleaving-omission (the interleaving is in the model), unread-code (read at [17], edited at [130]), budget (fixed at [95]), reporting-gap (it was never discovered).

### 5.7 Minimal interception point

Add a "consumer precondition audit" item to **03 update analysis or 05 completeness review**:

- **Subject**: every statement in the update that clears, resets or reassigns some state (here `packetsNotCommitted.clear()`), and the code that is **unchanged** but reads this state (here the COMMIT branch `Learner.java:643-646`).
- **Product**: a table with columns "consumer | implicit precondition (dereference, `peekFirst/Head`, `get`, iterator) | can the update make it false | which branch or error flag in the model corresponds". For each "can", two things must be given:
  - A reachability canary of the form "the consumer action can fire while the precondition does not hold", that is, the `NPEWindowNotReached` above. On v1's model it is violated in 27 seconds and would expose this abstraction directly.
  - An instrumentation point that puts the probe at the **entry** of the consumer and records the precondition-related quantity (for example the buffer size).
- Additional rule: every guard in the model that has no counterpart check in the implementation (for example v1's `syncBuf /= <<>> ∧ Head(syncBuf) = e`) must be justified one by one in 05.
