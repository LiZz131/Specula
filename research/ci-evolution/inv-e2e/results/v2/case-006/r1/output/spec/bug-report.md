## Bug 1 (MC-1): Reused ReadIndex context released by an acknowledgement produced for the earlier request

- **Scenario**: U2 (mechanism) and U3 (consequence)
- **Severity**: Medium
- **Invariant violated**: `UpdReadAckFresh` (instance-bound acknowledgement)
  and `UpdReadIndexLinearizable` (read index covers every entry committed
  before registration)
- **Configs / counterexamples** (all from Init):
  - `Update_hunt_stale_ack.cfg` — `UpdReadAckFresh`, 21 states, BFS-shortest:
    `spec/output/mc-upd_hunt_stale_ack.log`,
    `spec/output/cex/upd_hunt_stale_ack.{json,tla,steps.md}`
  - `Update_focused.cfg` — `UpdReadAckFresh`, 19 states:
    `spec/output/mc-upd_focused.log`, `spec/output/cex/upd_focused.{json,tla,steps.md}`
  - `Update_full.cfg` simulation over the complete `MCNext` —
    `UpdReadAckFresh`, 47 states, via the forwarded-read path:
    `spec/output/mc-upd_full_sim.log`, `spec/output/cex/upd_full_sim.{json,tla,steps.md}`
  - `Update_hunt_linearizable_directed.cfg` — `UpdReadIndexLinearizable`,
    35 states: `spec/output/mc-upd_hunt_linearizable_directed.log`,
    `spec/output/cex/upd_hunt_linearizable_directed.{json,tla,steps.md}`

### Trace Summary (directed counterexample, `UpdReadIndexLinearizable`)

1. s1 campaigns, wins term 1 (votes from s2), appends its no-op, replicates
   to s2 and s3, and commits index 1 (states 2-13; Ready persistence steps
   interleaved as the persist-before-send contract requires).
2. s1 registers read `ctx1` at index 1 (stamp 1) and broadcasts heartbeats
   carrying `ctx1` (state 14).
3. s2 acknowledges; s1 releases `ctx1` and — new with the update — frees the
   pending entry (states 15-16).
4. s2 campaigns for term 2 (state 17). s3 handles s1's term-1 heartbeat and
   sends a `MsgHeartbeatResp{term 1, ctx1}` that stays in flight (state 20).
5. s3 votes for s2; s2 becomes leader of term 2, replicates its no-op and
   commits index 2 (states 24-33). No term-2 message reaches s1.
6. s1, still leader of term 1, registers a new read with the same context
   `ctx1` at its commit index 1 (stamp 2; highest committed index anywhere is
   2) (state 34).
7. s3's delayed term-1 response arrives; `recvAck` counts it for the new
   registration and s1 releases the read with index 1, using an
   acknowledgement generated before the registration (state 35).

### Root Cause

`read_only.go:103` (the update) deletes released requests under their real
key, so `addRequest` (`read_only.go:52-59`) accepts a new request with a
context that was released earlier in the same term. Acknowledgements are
matched to pending requests only by `string(m.Context)`
(`read_only.go:64-73`); heartbeats and their responses carry no
per-registration identity (`raft.go:427-443`, `raft.go:466-473`,
`raft.go:1112-1115`). `stepLeader` releases the request once the count
reaches quorum (`raft.go:915-932`), even when the counted response predates
the registration. Before the update the stale map entry made the second
`addRequest` a no-op, so the trigger was masked (at the cost of never
answering the reused context).

### Affected Code

- `read_only.go:100-105` (`advance`): frees released requests (update).
- `read_only.go:52-59` (`addRequest`): context-keyed deduplication.
- `read_only.go:64-73` (`recvAck`): acknowledgement keyed only by context.
- `raft.go:915-932` (`stepLeader` `MsgHeartbeatResp`): quorum release.
- `raft.go:831-833`: in-code note suggesting an internally defined context.

### Reproduction

`harness/repro.sh` → `spec/output/repro.log`: on the update revision
`TestSpeculaReproStaleReadAfterContextReuse` fails with
`STALE READ: ReadState{Index:2, ctx:"ctx1"} returned for a request issued after index 3 was committed in term 2`;
on the baseline revision the same schedule produces no ReadState (the reused
context is never registered). The unique-context control passes on both.

### Recommendation

Bind acknowledgements to a registration (internal read id or heartbeat round
recorded at registration; ignore older responses), or reject reuse of a
context within a term. Keep the update's freeing of released requests.
